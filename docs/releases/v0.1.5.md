# Rewind64 v0.1.5 — Linux x86-64 experimental prerelease

**Explore execution. Trace every instruction. Understand the past.**

This experimental release strengthens observability of signals affecting one explicitly launched tracee. It is **not a stable debugger** and does **not implement recording or reverse execution**.

## Changes since v0.1.4

- Added Assembly-only signal-stop diagnostics to the Linux ptrace debugger. When the kernel reports a signal-delivery stop during stepping or process continuation, Rewind64 reports the signal number and counts the stops forwarded to the target.
- Final output shows **`Signals forwarded: N`** alongside `Steps completed: actual / requested`. The count represents debugger-observed signal stops, not a proof that a target application handled or acted on every signal.
- Added `tests/fixtures/handled_signal.asm`: a native x86-64 Assembly program that installs a `SIGUSR1` handler using Linux `rt_sigaction`, sends two `SIGUSR1` signals to itself, returns through `rt_sigreturn`, and exits successfully only after both handlers run.
- Expanded Bash integration checks to validate both ordinary and `--changes-only` views with repeated handled signals. Existing SIGTRAP, SIGSEGV, SIGTERM, early-exit and clean-exit checks now validate signal accounting as well.
- Kept all executable debugger logic and test fixtures in NASM Assembly. No Python source, runtime, or test dependency was introduced.
- GitHub Actions verifies Linux x86-64 builds and tests on Ubuntu 22.04 and 24.04 before publication.

## Commands

```sh
./rewind64 --version
./rewind64 run --steps 2 /path/to/authorized/program
./rewind64 run --changes-only --steps 2 /path/to/authorized/program
```

Output is for human debugging, not a stable structured protocol. Signal-stop counting is observational and may not match signal-handler invocation counts for every program.

## Download and verify

Download `rewind64-v0.1.5-linux-x86_64.tar.gz` and `SHA256SUMS.txt` from this prerelease and verify the archive checksum before use.

## Limitations

- Linux x86-64 with glibc and normal ptrace permissions only.
- One explicitly launched tracee; no attach, breakpoint management, interactive debugging, thread/fork following, trace file, historical navigation, Windows/macOS binary, or deterministic replay.
- The tracer does not isolate executable behavior; target programs run with the user's inherited privileges and environment. Only debug authorized executables.
- Errors and target exit statuses can overlap; unusual ptrace events, group stops, and complex multithreaded signal scenarios still require testing.
