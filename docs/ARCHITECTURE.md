# Architecture and ABI notes

## Current scope

`main` supports `--help`, `--version`, the target-free JSON discovery command `--capabilities`, and `run`. `run` parses exactly one execution mode: `--steps N` (1..64, default 1), `--observe-only` (zero steps) or `--interactive` (stop-time console), and optionally `--changes-only`, in any order before the target; `--` terminates option parsing. The three execution mode flags are mutually exclusive. Duplicate flags are rejected. `debug_run` accepts a null-terminated `argv` vector and is available only in the Linux/x86-64 build.

All executable debugger implementation in this milestone is Assembly in `src/cli/main.asm`, `platforms/linux/debugger.asm`, `src/registers/x86_64.asm`, and `src/registers/delta.asm`. The black-box test runner is Bash orchestration using native Assembly test fixtures; **Python is not required or used**. `Makefile` describes assembly and link steps. The program uses libc as an OS/API wrapper layer; no high-level language source file implements debugging logic.

## Static CLI capability discovery (v0.2.14 development)

The Linux CLI compares `--capabilities` exactly using libc `strcmp` and verifies that `argc==2` before calling `puts` on an immutable, assembled JSON string. Its version, platform, ptrace backend, execution-mode limits, read-only inspection sizes and unsupported feature booleans are **compile-time declarations**. This path does not call `debug_run`, `fork`, `ptrace` or `execvp`; it does not detect runtime tracing permission. Extra arguments result in exit code 2. `docs/CLI_CAPABILITIES.md` documents schema 1 and consumer compatibility requirements. The native Bash suite verifies the reported compile-time values and, when `jq` is installed, parses JSON; it retains zero Python dependencies.

## v0.2.15 final-line input normalization (development)

The debugger reads operator input into the existing 64-byte stack-local `SESSION_BUFFER` using `fgets`. The established overlong-line guard rejects a full 63-byte payload with no LF and drains the entire remainder rather than executing a suffix. Only a **short input that ends without LF** enters the new normalization path: `strlen` determines its length, the last byte is checked for LF, and a synthetic LF followed by NUL is appended in the already allocated buffer. The maximum accepted 62-byte command can therefore occupy bytes 0..61, LF byte 62 and NUL byte 63 without overflow. Newline-terminated input is never rewritten.

This makes bare `regs`, `status`, `code`, `stack`, `bytes`, `history`, `help`, `step`, `continue`, `quit`, and their supported aliases behave at a final EOF-terminated line exactly as they do with LF. Existing numbered-command parsers remain strictly validated. An empty EOF read still takes the cleanup-and-reap path. New regressions confirm no unintended steps or signal delivery on read-only inspection, proper cleanup on implicit EOF, and no prefix-command confusion.

The development v0.2.15 prerelease publishing workflow adds a **two-runner verify matrix** for Ubuntu 22.04/24.04 with `needs: verify` on the publishing job. A failure on either runner blocks packaging and release publication, independent of branch PR checks. The publishing runner repeats `make clean && make test` to verify the exact packaged source.

## v0.2.16 opt-in exec-event stops (published experimental)

Interactive `until-exec` / `v` sets `WAIT_NEXT_EXEC` in the last available disjoint dword of the existing aligned 1344-byte debugger stack frame (`rbp-1344`). It explicitly disables `WAIT_NEXT_SIGNAL` and cancels any pending interactive step batch. Normal `PTRACE_CONT` resumes to kernel stops; validated application signal-delivery stops are counted and forwarded normally, without interrupting the opt-in exec watch. Exec and exit event numbers remain classified independently of application SIGTRAP.

At a real `PTRACE_EVENT_EXEC`, the debugger increments the exec-event counter, emits the existing event diagnostic and **pauses only when `WAIT_NEXT_EXEC` is armed**. It clears the armed flag and pending-signal slot, refreshes all 216 bytes of Linux x86-64 registers with `PTRACE_GETREGS`, copies the current state into the baseline `PREVREGS`, clears the 16-entry RIP ring and records the **new image's RIP** labeled with the cumulative verified step count. A later user step therefore compares registers from the same executable image, not stale ones. Previous image RIPs are discarded for this opt-in transition; there is no persistent trace and no replay. At EOF or `quit`, the tracee is terminated and reaped without any synthetic signal injection. If no exec event occurs, the target exits or signals normally with actual process status. Ordinary `continue`, `until-signal`, bounded automatic stepping and non-interactive observation remain unchanged.

Fixed input matching rejects arguments or case variants such as `until-exec 1` and `V`; a final command without LF is already normalized by v0.2.15. The 16 new native Bash/NASM regression scenarios cover real exec, alias, inspection, stepping, old-image history clearing, signals before exec, pending faults, no-exec termination, extra arguments, compact output and EOF. **259/259 verified** on Ubuntu 22.04 and 24.04 in final PR-head and merged-main CI.

### First single-step after an exec event

Linux may report a synthetic `TRAP_BRKPT` with **unchanged RIP** on the first single-step requested immediately after a genuine `PTRACE_EVENT_EXEC`. The debugger's `WAIT_NEXT_EXEC` state has values `0=off`, `1=awaiting exec`, `2=first post-exec step` and `3=one redundant stop already consumed`. For that narrowly scoped first step, Rewind64 checks the previous instruction bytes and rejects actual INT3 (`cc`), `INT 3` (`cd 03`) and ICEBP (`f1`) as synthetic steps. If the RIP has not advanced and the state is 2, it retries exactly **one** `PTRACE_SINGLESTEP` with signal zero; the redundant stop is not counted or forwarded. A second unchanged-RIP trap is not retried. Only successful verified instruction completion increments the step count, and real signal-delivery stops still follow the existing pending-signal rules. The new regression suite separately proves that a genuine INT3 *after* the first instruction is delivered to the application.

## v0.2.17 finite RIP watches (development)

A stopped interactive tracee may accept `until-rip 0xHEX`. The command validates exactly 1–16 hexadecimal digits after the `0x`/`0X` prefix and requires an immediate newline or EOF. The debugger compares the requested address to the **current stopped RIP** and reports an immediate hit without resuming if already equal. Otherwise it issues `PTRACE_SINGLESTEP` up to **64 confirmed instruction completions** without writing to the target or enabling a hardware/software breakpoint. Each confirmed step refreshes the 216-byte register snapshot, updates the baseline, increments the cumulative step count, and records the new RIP. Intermediate register dumps are suppressed, but final hits show the fresh snapshot. Exhaustion returns to the stopped prompt after exactly 64 confirmed steps, without resuming beyond the bound.

The aligned debugger stack frame increases from **1344 to 1376 bytes**, retaining all existing offsets and adding a disjoint address qword at `rbp-1352..-1345`, active dword `rbp-1356..-1353`, remaining-budget dword `rbp-1360..-1357`, and starting cumulative step dword `rbp-1364..-1361`. No heap, code patch, target memory write, trace recording or process attach is involved.

A **real signal-delivery stop** cancels the watch and returns to the existing pending-signal interactive prompt. `PTRACE_EVENT_EXEC` invalidates old-image addresses: it cancels the watch, refreshes the baseline and RIP history for the new image, and leaves the tracee stopped. A natural target exit returns the real process status. This bounded address watch is not an INT3 software breakpoint, will not run beyond 64 verified instructions, and cannot catch addresses reached only after the budget. Persistent breakpoints and re-arming remain in Issue #25.

## Debugger state machine

1. `fork()` once; child requests `PTRACE_TRACEME` and calls `execvp` with the caller-provided argument vector.
2. Parent `waitpid`s for the `exec` stop, verifies the initial stop is a `SIGTRAP` caused by the traced exec and requests `PTRACE_O_EXITKILL`, `PTRACE_O_TRACEEXEC`, and `PTRACE_O_TRACEEXIT` before resuming the target. Early child exit and signal termination remain separately classified.
3. `PTRACE_GETREGS` captures the 216-byte Linux x86-64 `user_regs_struct`. `src/registers/x86_64.asm` prints general-purpose registers (RAX, RBX, RCX, RDX, RSI, RDI, RBP, R8–R15), RFLAGS, FS_BASE and GS_BASE. The Linux backend prints RIP and RSP. This module is architecture-specific, not a generic register layout for other operating systems.
4. `--interactive` enters a stop-time command loop **after the initial register snapshot**. Commands `step [N]`/`s [N]`, `until-signal`/`u`, `history [N]`/`h [N]`, `events`/`e`, `signals [N]`/`g [N]`, `regs`/`r`, `status`/`i`, `code`/`x`, `bytes [N]`/`b [N]`, `stack`/`k`, `continue`/`c`, `help`, and `quit`/`q` are matched by libc `strcmp` against newline-terminated `fgets` input; `mem 0xHEX [COUNT]` / `m 0xHEX [COUNT]` is handled by a strict NASM hexadecimal and bounded decimal-count parser. The prompt is flushed via `fflush` so it is visible even while waiting. `step [N]` executes 1–16 individually verified instructions (default one) and returns to the prompt when the requested count is complete or on a verified application signal-delivery stop; count parsing rejects leading zeros, signs, extra whitespace and trailing garbage; `history [N]` prints at most 16 debugger-local RIP samples (initial stop and verified synthetic step completions) tagged with their verified absolute instruction-step indexes, optionally restricted to the latest strict decimal N=1..16 samples without resuming or reconstructing past state; `events` / `e` reads debugger-owned counters and last valid signal-delivery stop's signed `si_code` without ptrace reads or resuming; `signals [N]` / `g [N]` presents up to eight validated signal-delivery stops with signed code and step number from fixed-size local memory without calling ptrace or forwarding, optionally selecting the latest strict decimal N=1..8 entries and preserving retained-history index labels across wraparound; `regs` calls `PTRACE_GETREGS` and prints all CPU fields; `status` displays the PID, confirmed steps and pending signal; `code` obtains fresh RIP with `PTRACE_GETREGS` and reads one eight-byte word from that address using `PTRACE_PEEKTEXT`, without modifying the tracee; `bytes` gets the stopped RIP and reads a single eight-byte little-endian word via `PTRACE_PEEKTEXT`, reporting 1–8 low-to-high bytes without disassembly; `stack` obtains fresh RSP and uses `PTRACE_PEEKDATA` to read exactly four consecutive eight-byte words starting there, stopping without resuming on any read error; `mem`/`m` reads between one and four eight-byte words at explicitly validated contiguous 64-bit addresses via `PTRACE_PEEKDATA`, without resuming the tracee; `until-signal` / `u` starts the existing `PTRACE_CONT` event/signal loop with an opt-in flag and returns to the interactive prompt on the next verified application signal-delivery stop while leaving that signal pending (or ends normally on target termination), forwarding a previously pending signal once on the successful resume; `continue` uses the existing `PTRACE_CONT` event/signal loop and forwards any pending signal; `quit`/EOF requests shutdown and a bounded reap without delivering the pending signal. `--observe-only` captures initial state, skips the step loop entirely, and immediately uses `PTRACE_CONT` to follow events and signals until termination, producing `Steps completed: 0 / 0`. Otherwise, `PTRACE_SINGLESTEP` advances up to 64 requested instructions. `PTRACE_GETSIGINFO` classifies trace-step traps (`TRAP_TRACE`); where Linux reports `TRAP_BRKPT` while stepping a `syscall`, `PTRACE_PEEKTEXT` verifies the previous RIP contains the `0f 05` opcode. Application-generated `SIGTRAP`/`INT3` remains forwarded rather than counted as a step. The current register snapshot is captured after each confirmed completed step. The CLI's optional `--changes-only` display mode hides full repeated register tables but does not alter kernel sampling or delta comparison.
5. Two 216-byte register buffers are reserved at non-overlapping offsets in the Linux debugger's stack frame, one for the previous step and one for current state. `src/registers/delta.asm` compares 20 displayed register fields, prints only changed values, then the debugger copies the current snapshot into the previous buffer for the next step. **No snapshots are saved to disk, and this is not reverse execution.**
6. When `waitpid` exposes an event number in status bits 16..31, the debugger recognizes `PTRACE_EVENT_EXEC` and `PTRACE_EVENT_EXIT` and resumes the stopped tracee with signal 0. Synthetic ptrace event SIGTRAP stops do not increment the forwarded-application-signal counter. Unexpected event numbers produce an explicit tracing error; there is no general process/thread event manager. The debugger counts observed exec/exit events for diagnostic output. At an exit event, `PTRACE_GETEVENTMSG` retrieves the kernel-supplied unsigned machine-word status payload, displayed as `raw_wait=0x...` (event-time data, not the final `waitpid` return).
7. `PTRACE_CONT` resumes the target; the parent reports exit status or termination signal and prints the completed/attempted instruction-step count. When the parent observes an application signal-delivery stop, it logs the signal number and increments a per-tracee counter before resuming with that signal. The terminal diagnostic `Signals forwarded: N` counts successfully requested nonzero-signal ptrace resumes, **not** merely observed signal stops, signal-handler invocations or a guarantee that the target processed the signal. When an interactive step or counted batch is interrupted by an application signal, the debugger cancels all remaining batch steps, retains the signal in its pending-signal slot and returns to the prompt. A subsequent `step` injects it once through `PTRACE_SINGLESTEP`; `continue` injects it once through `PTRACE_CONT`; `quit`/EOF does neither. Signal-delivery logging includes signed `siginfo_t.si_code` at offset 8, distinguishing `SI_USER`, `SI_TKILL`, and kernel fault signals when supported. Only for `si_code == SI_USER (0)` or `SI_TKILL (-6)` are sender PID (offset 16) and UID (offset 20) read from the `siginfo_t` union; other codes must not be interpreted as sender metadata. Subsequent stops forward application signals including generated SIGTRAP.
8. Ordinary signal-delivery stops are verified with `PTRACE_GETSIGINFO`; an `EINVAL` result identifies a Linux job-control group stop, which the current TRACEME backend cannot resume correctly. The prototype reports an explicit unsupported group-stop error and cleans up the child rather than repeatedly forwarding `SIGSTOP`.
9. On debugger errors, cleanup sends `SIGKILL` and loops through intermediate `waitpid` stopped states (including synthetic `PTRACE_EVENT_EXIT`) with zero-signal `PTRACE_CONT` until the child has been reaped or a bounded stop budget is exhausted. This is defensive best-effort recovery, not a guarantee in every pathological scenario. A target exiting or being signaled before the expected ptrace stop is separately reported.

Currently there is a **single** target process/session, up to 64 bounded automatic steps or multiple operator-requested interactive steps, and no thread event management, disassembler, breakpoint insertion, `attach`, or memory explorer. Interactive prompt control is provided at initial stop, recognized single-step completions and verified signal-delivery stops during stepping. Synthetic exec/exit ptrace events cancel a remaining interactive batch and can still transition to automatic continuation; unusual unsupported stops can transition to cleanup instead of restoring a prompt. Targets that fork children, create threads, or use complex trap/signal behavior are not fully supported. No recording and no replay are present. System security policies are never bypassed.

## v0.2.13 filtered signal-history view

The eight-entry signal-stop ring remains **128 bytes** (8 records × 16 bytes) in debugger-local stack memory. Two dword metadata fields at `rbp-1336` (`SIGNAL_RING_LIMIT`) and `rbp-1340` (`SIGNAL_RING_SKIP`) fit into unused space in the existing 1344-byte aligned debugger frame. They do not overlap the ring (`rbp-1312..-1185`), command buffer or prior register snapshots.

- Bare `signals`/`g`, including EOF without a newline, defaults to the entire retained ring. `signals N`/`g N` accepts only one ASCII digit 1–8 followed immediately by newline or EOF.
- For a request N, the view clamps the limit to the retained count and computes `skip = stored - limit`. Physical ring slot `(start + skip + view_index) & 7` correctly handles the wrap index; labels use `skip + view_index`, retaining the original 0–7 order.
- Empty history displays an explanatory message; invalid counts return to the same stopped prompt with a usage hint. Neither filtering, reading a ring entry nor displaying it calls `ptrace`, resumes the target, or forwards a pending signal.
- The integration suite adds 13 bounded-filter regressions, including empty/single-entry clamps, 10-event wraparound, aliases, malformed counts, stopped SIGILL, repeated read-only inspection, compact output, and newline-free EOF. Expected total: **217** (prior 204 + 13), pending CI verification.

## Calling convention

- ABI: System V AMD64; caller and callee follow 16-byte alignment at call sites.
- Linux `ptrace` API: `ptrace(request, pid, addr, data)` as exported by libc.
- Linux C library functions used: `fork`, `execvp`, `waitpid`, `ptrace`, `kill`, `printf`, `puts`, `perror`, `_exit`, `strcmp`, `fgets`, `strlen`, `getchar`, and `fflush`.
- Registers in a reserved stack region use the Linux x86-64 kernel's `user_regs_struct` offsets: R15(0), R14(8), R13(16), R12(24), RBP(32), RBX(40), R11(48), R10(56), R9(64), R8(72), RAX(80), RCX(88), RDX(96), RSI(104), RDI(112), RIP(128), RFLAGS(144), RSP(152), FS_BASE(168), GS_BASE(176). These offsets are **not portable** to other architectures or OSes.
- All `main` arguments come from the C runtime; targets run with the caller's inherited environment and permissions.

## Read-only code-word inspection

The interactive `code`/`x` command displays a single eight-byte x86-64 little-endian machine word starting at the **current** RIP. This is intentionally not an arbitrary-address memory browsing interface and **does not disassemble** or modify tracee code. A successful `PTRACE_PEEKTEXT` call can return `-1` when the memory contains eight `0xff` bytes. The NASM handler first sets thread-local `errno = 0` using libc `__errno_location`; only when the result is `-1` and `errno != 0` does it display a ptrace failure and return to the prompt. It refreshes CPU registers before reading and preserves any pending delivery signal without resuming the process. `tests/fixtures/all_ones.asm` verifies the valid `-1` data path by inspecting the entry word and quitting without running it.

## Resume until a genuine signal-delivery stop

The v0.2.12 interactive `until-signal` / `u` command sets a debugger-owned dword flag at `WAIT_NEXT_SIGNAL=-1332` in the existing 1344-byte aligned `debug_run` stack frame. Unlike `step` it uses `PTRACE_CONT` rather than `PTRACE_SINGLESTEP`; unlike ordinary `continue` it retains the pause-on-valid-signal flag across ptrace exec events and stops at the next Linux `PTRACE_GETSIGINFO`-validated application signal-delivery stop. When such a stop is classified and recorded, the flag is cleared, the signal remains pending, the remaining interactive batch is canceled, and the command loop resumes with lifecycle and bounded `signals` history available for read-only inspection. A future `u`, `step`, or `continue` forwards this pending signal once on successful resume, using existing injection accounting. A `quit` or EOF without resuming terminates/reaps the tracee without forwarding. If the target exits, the command returns the real exit status without fabricating a pending signal or history record. Ordinary `continue` clears the flag and keeps its original automatically forwarding behavior. A native Assembly fixture emits ten successive SIGUSR1 signals with a real handler, verifying eight-slot ring wrap, prompt frequency, and separate observed/forwarded totals. **This is forward execution**, not a retroactive trace, deterministic replay, or reverse debugging.

## Bounded read-only signal-stop history

The v0.2.11 native NASM `signals` / `g` inspection command lists up to **eight** validated application signal-delivery stops in chronological order, including signal number, signed Linux `siginfo_t.si_code` and cumulative verified instruction step count. At each `PTRACE_GETSIGINFO`-validated stop, a fixed-size 16-byte record stores three dwords (signal, code, step), leaving four bytes reserved; a power-of-two modulo ring overwrites the oldest entry after eight records. The 8×16-byte ring occupies `debug_run` stack offsets -1312..-1185, with disjoint dword index/count/print metadata at -1328..-1313, below the existing history and lifecycle fields. The stack frame increases from 1184 to 1344 bytes, preserving 16-byte ABI alignment. The debugger never writes tracee memory. A synthetic step trap, ptrace exec/exit event, invalid command or ordinary read-only inspection is not a validated application signal-delivery stop and cannot insert a record. `signals` is read-only; calling it at a pending-signal stop neither resumes the tracee nor delivers the signal. Exact `signals` and `g` forms also work on final EOF without newline. It does not track full register/memory states, and is not reverse execution, a persisted event log or deterministic replay.

## Read-only process lifecycle diagnostics

The v0.2.10 interactive `events` / `e` command prints debugger-local lifecycle counters at a stopped prompt: PID, verified forward step completions, **validated application signal-delivery stops**, **nonzero signal injection requests accepted by ptrace**, pending signal, and ptrace exec/exit event totals. A second line displays the most recent validated signal number and signed `siginfo_t.si_code` only if a real signal-delivery stop has been classified. No signal data is inferred from synthetic single-step traps or ptrace exec/exit events. The observed-stop count is incremented after successful `PTRACE_GETSIGINFO` classification; the forwarding count is maintained on successful nonzero-signal `PTRACE_SINGLESTEP` or `PTRACE_CONT` calls. These are deliberately **different** metrics: forwarding is not proof that the target handled the signal. Three dword locals at -1164, -1168 and -1172 are distinct from the existing dual history rings and aligned within the pre-existing 1184-byte stack frame. A `printf` call temporarily allocates an aligned 16-byte varargs area for the seventh and eighth arguments. The command itself does not resume the target, read tracee memory or alter pending signals. Exact commands accept a final line without a newline. The debugger currently resumes automatically after ptrace exec/exit events, so an interactive prompt cannot be assumed to occur at those event boundaries.

## Bounded RIP observation history

The v0.2.8 interactive `history` / `h` command prints the most recent **16** observed instruction pointers, oldest first, without resuming the target. In v0.2.9 the optional strict `history [N]` / `h [N]` request displays only the last 1–16 stored entries, clamping N to available history, and prints a cumulative confirmed step number for each sample (initial post-exec state is step 0). It is a narrow troubleshooting aid, not a general trace format or reverse execution mechanism. A fixed 128-byte ring at debugger stack offsets -1024..-897 stores 16 qword RIP samples, separated from register buffers, input text and ptrace siginfo. Metadata at -892..-880 stores the oldest print slot, print index, next overwrite slot and entry count. The v0.2.9 debugger stack frame is 1184 bytes (16-byte aligned), with a second disjoint 128-byte ring at -1152..-1025 for the associated absolute instruction step numbers and bounded display-filter fields at -1160..-1153. Previous entries' step numbers do not change when the circular buffer wraps. The ring records the initial exec stop and each confirmed single-step completion after `PTRACE_GETREGS` and register snapshot copying, with the cumulative confirmed step count incremented before recording the new step sample. Signal-delivery stops, ptrace exec/exit events, memory reads, invalid commands and pure inspection commands do not create history entries. Once 16 samples are present, the next write replaces the oldest, with modulo-16 arithmetic, and the display reconstructs chronological order. The contents disappear on termination: there is **no disk I/O, CPU-state reconstruction, state rollback, trace recording, or replay**.

## Bounded read-only instruction-byte inspection

The v0.2.7 `bytes [N]` and `b [N]` commands provide a byte-oriented view of the current RIP (default eight bytes, explicit count 1–8). This is deliberately **not a disassembler**. The NASM command parser accepts a single decimal digit from 1 through 8, rejects malformed/extra input, and never resumes the tracee for validation failures. The command obtains fresh CPU registers, clears thread-local `errno`, performs exactly one `PTRACE_PEEKTEXT` word read, and checks `errno` when the return value is `-1`. A valid all-ones word yields eight `ff` bytes rather than a false failure. The little-endian 64-bit word is shifted by each byte offset and masked to print individual bytes in ascending address order. Both limit and index occupy separate debugger-local stack slots outside the 64-byte input buffer and CPU snapshots. The target is never modified; unreadable text causes a nonfatal prompt return and pending signals are not forwarded.

## Bounded read-only stack inspection

The new `stack`/`k` command reads **four 64-bit words (32 bytes)** from the tracee's current RSP while it remains stopped. The NASM state holds a saved stack base, a word index bounded to 0..3, and the current peek result in non-overlapping slots of the debugger frame. The command refreshes `user_regs_struct` with `PTRACE_GETREGS` before reading, computes `RSP + index*8` for each word, and never follows stack pointers or accepts arbitrary addresses. It uses `PTRACE_PEEKDATA` and the same explicit `errno` reset/check strategy as RIP code inspection: a `-1` return with `errno=0` is valid all-ones data. An unreadable word results in `perror` and a return to the prompt; the target remains stopped and any pending signal remains pending. The debugger never writes target memory or registers. Two native NASM fixtures exercise deterministic stack contents and an unmapped RSP; tests inspect the invalid stack state and quit safely without resuming target instructions.

## Strict bounded address inspection

Interactive `mem 0xHEX [COUNT]` / `m 0xHEX [COUNT]` reads **one to four eight-byte words (8–32 bytes)** at consecutive addresses in the single process launched by Rewind64. If COUNT is omitted, the command retains its original one-word behavior. The NASM parser accepts precisely the prefix `0x` or `0X` followed by 1–16 hexadecimal digits, up to 64 bits. It rejects signs, missing digits, nonhex characters and an excess (17th) digit, plus counts outside the one-digit decimal range 1–4, extra spaces and trailing arguments before attempting ptrace. It computes the address with four-bit shifts/or operations, checks the last requested address for 64-bit wrap before reading, and stores the base, current address, count, index and peek result in disjoint stack slots separate from the 64-byte input, signal state and register snapshots.

The debugger clears libc `errno` before **every** `PTRACE_PEEKDATA` call. Because `-1` is valid all-ones memory data, the command treats it as an error only when `errno` is nonzero; errors are logged and the prompt remains available with the tracee stopped. Reads never inject a pending application signal. The command stops on the first unreadable word, does not write memory or follow pointers, and cannot dump arbitrarily long regions. Any invalid range or interrupted read returns to the same prompt without forwarding a pending signal. Bash tests resolve the `words` and `_start` symbols from native Assembly ELF fixtures using `nm` rather than assuming a hard-coded address; test scenarios include missing/bad/overflowing hex, mapped data, all-ones data, unmapped pointers, repeated reads and SIGILL-pending inspection.

## Reliability / planned hardening

- Interactive counted steps store their remaining budget in a separate 32-bit local stack slot outside the input buffer, register snapshots and siginfo structure. Each successful synthetic step trap decrements the remaining budget exactly once; a signal stop or ptrace event cancels it. There is no unbounded interactive batch or implicit signal reinjection.
- The Assembly session uses a bounded 64-byte command buffer, newline-terminated text commands, and stdin EOF as an explicit quit/cleanup request. A 63-byte input fragment without newline triggers a drain through the next newline or EOF; the full overlong line is rejected rather than interpreting remaining bytes as another command. Command scripts can exercise it without a TTY, but interactive use is not yet a full job-control or terminal-management implementation.
- The waitpid helper retries on EINTR. Native Assembly fixtures exercise SIGTERM, SIGSEGV, SIGILL, SIGFPE, SIGTRAP, repeated SIGUSR1 and handler `rt_sigreturn`, explicit group-stop detection/cleanup, several exit statuses, and the 64-step bound. Correct continuation *through* group stops, multi-threaded signals, and more lifecycle variants remain unimplemented.
- Observing `PTRACE_EVENT_EXEC`/`PTRACE_EVENT_EXIT` is not equivalent to following forks, tracking threads, or recording execution history. Explicit multi-thread/process follow and stateful interactive sessions are not implemented.
- `PTRACE_O_EXITKILL` reduces orphaned debuggees on debugger crashes but does not replace thorough lifecycle cleanup testing.
- Target exit statuses overlap the debugger's own error codes; machine-readable status separation is future work.
- A future trace format must be versioned, bounds-checked, and tested with corrupt inputs. State snapshots are not equivalent to deterministic replay.
